# Agent Memory System

**给 AI Agent 用的跨会话长期记忆系统。** 数据库为唯一真相源，注入上下文的工作层只是从库里提炼出来的视图——换模型、换框架、换部署环境，记忆不丢。

纯标准库实现（Python 3.8+），零第三方依赖，不需要修改宿主平台源码。

---

## 它解决什么问题

大多数 Agent 的"记忆"就是一段几百到几千字符的注入文本。结果：

- 写满了只能覆盖，覆盖就丢；
- 记住了什么、为什么记、从哪条对话来的，全都查不到；
- 换一次模型或客户端，记忆体系跟着重来；
- 规则文档里写死"每天整理一次"，改了频率忘了改文档，文档从此骗人。

这套系统把记忆拆成两层：**完整底本放数据库，精简视图进上下文**。视图满了从库里重新提炼，一条不丢；每条视图末尾挂 `@src:ID`，几秒内能追回原文。

## 架构

```
┌──────────────────────────────────────────────┐
│   memory.db  (SQLite, 唯一真相源)              │
│   完整原文 + 标签 + 情绪 + 重要度 + 时间戳      │
└──────────────┬───────────────────────────────┘
               │  提炼 · 排序 · 合并（单向）
               ▼
┌──────────────────────────────────────────────┐
│   USER.md / MEMORY.md  (工作层)                │
│   每轮注入上下文，容量小，每条挂 @src:ID        │
└──────────────────────────────────────────────┘

辅助：
  growth_log.md     过程叙事（候选洞察、复盘草稿）
  memtool.py        唯一写入路径（13 个子命令）
  sleep-consolidation skill   整理流程（12 步）
  backups/          改动前快照
```

**数据只从库流向工作层，不反向。** 工作层写坏了、写满了、被平台工具污染了，从库重新生成一份即可。

## 快速开始

```bash
# 1. 初始化（建目录、建库、写 3 条系统规则、生成 skill 骨架）
python memtool/memtool.py init --agent "<你的 agent 名字>"

# 2. 自检（任何 [FAIL] 都要先解决）
python memtool/memtool.py selfcheck

# 3. 记第一条
python memtool/memtool.py add \
  --summary "一句话标题" \
  --content "完整内容" \
  --tags "分类1,分类2" --importance 4

# 4. 体检工作层
python memtool/memtool.py check --show
```

`init` 可以重复运行：已存在的文件不覆盖，已入库的系统规则不重复插入。

## 命令速查

| 命令 | 干什么 |
|---|---|
| `init` | 建目录/建库/写骨架/生成 skill（幂等） |
| `selfcheck` | 环境自检，11 项 |
| `add` | 入库。优先 `--json 文件`（多行/含引号必用） |
| `search` | 关键词检索，OR 语义，按命中数排序 |
| `show` | 看完整记录 |
| `retire` | 退役（合并/过期/写错），原文保留 |
| `promote` | 草稿转正 |
| `link` | 建两条记忆的关联 |
| `forget` | 物理删除（需 `--yes`，仅限"忘掉某件事"） |
| `anchor-last` / `anchor-add` | 整理锚点：处理到哪个会话、入库几条 |
| `stats` | 统计 + 上次锚点 |
| `check` | 工作层体检：容量、`@src` 真伪、格式、指错检测 |

`--root` / `--db` / `--config` 可覆盖默认路径。默认 root = 脚本上级目录。

## 五个必须认识的坑

都是实测踩出来的，写在手册第 4 节：

1. **`status=草稿/正式` 不要做成文档里的约定、代码里没实现的东西。** 文档和实现不同步，那句话就变成一句没人执行的空话。
2. **"格式合法但指错对象"比"完全没有来源标记"更难发现。** `@src:142` 格式对、ID 真实存在，但指向的是另一条不相干的内容——只查"有没有标记"抓不出来，必须核对指向内容的主题是否匹配。
3. **零入库必须记锚点。** 跳过它，下次会重扫同一批已看过的内容。"这次没有新内容"本身就是有效记录。
4. **写工作层前先出改动对比。** 容量满触发重写、或新增要同步，都先生成候选版逐条比对，确认后才写。省掉这步，用户不知道自己的记忆被改成了什么样。
5. **无人值守模式下不要改核心文件。** 定时任务没人盯着，任何改变"用户是谁""我是谁"的写入都要留到有人在场时确认——哪怕看起来显然是对的。

## 验收标准

搭完不是"文件创建了"就算完。以下全过才算：

- `selfcheck` 全 PASS（容量上限那条可以是 WARN）
- 能 `add` 一条，`search` 查得到
- 重复内容第二次 `add` 被识别为 DUP，不产生两条
- `anchor-add` 后 `anchor-last` 能看到
- `check` 能正确报出容量占比 / 缺失来源标记 / 占位符未填写
- 同一库跑两次 `init` 不报错、不产生重复
- `forget` 不加 `--yes` 会被拦住

## 适配其他平台

手册假设宿主平台具备三件事：

1. 能按需加载 skill（或把 skill 正文并入系统提示词）
2. 有会话历史可供整理（或能从日志里取）
3. 有一个自动注入的"长期记忆"文件位置（没有就自己模拟）

三个都没有也能跑：把 `memtool.py` 当纯命令行用，工作层文件定期手工贴进上下文即可。系统本身只依赖 SQLite 和标准库。

## 设计约束

**不要在任何规则文档里写死会随环境变化的数字。** 执行频率、容量上限、记录条数——这些会被按需调整，一旦写进文档就会在某次调整后悄悄过时。

文档里只写"去哪里查"，不写"是多少"：

| 会漂移的 | 真源 |
|---|---|
| 整理频率 | 调度系统的任务列表 |
| 工作层容量 | 宿主平台配置文件 |
| 当前记忆条数 | 数据库查询 |

唯一例外是**带时间戳的历史记录**——"某次把频率从每日改成每周"描述的是那一刻发生了什么，本来就不该变。
